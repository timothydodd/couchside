# CLAUDE.md

Couchside is a self-hosted media server for k3s. Go backend in `server/`, React frontend in `web/`, Helm chart in `deploy/helm/couchside`. The UI shares `../portside-lite`'s component classes and shell layout; its colours come from the C logo (see `docs/style.md`).

## Build & verify (WSL)

- Go 1.27: the `go` line in `server/go.mod` is the one source (CI, the release and the installer use `go-version-file`, and a CI step fails when the Dockerfile's `golang:` image differs). `~/.local/go/bin/go` is 1.23, but GOTOOLCHAIN=auto downloads 1.27 on first use.
  `cd server && ~/.local/go/bin/go vet ./... && ~/.local/go/bin/go test ./...`
- Builds, tests and smoke runs stay in the project: scratch work goes in the git-ignored `.tmp/` at the repo root (never `/tmp` or `C:`; a WSL restart wipes `/tmp`). For the web, `rsync` `web/` (without node_modules and dist) to `.tmp/web`, then run `npm ci && npx tsc --noEmit && npm run build` there, and `npm run lint` (oxlint, `.oxlintrc.json`; typescript-eslint doesn't support TypeScript 7) in `web/` itself, since oxlint skips paths under a dot folder like `.tmp`. Copy `package-lock.json` back if it changed.
- Full-stack smoke test: build the binary into `.tmp/`, then run it with `COUCHSIDE_DATA_DIR=.tmp/...`, `COUCHSIDE_WEB_DIR=.tmp/web/dist` and either `COUCHSIDE_MEDIA_ROOT` or none (a new data folder starts on the first-run setup). Generate sample media with `ffmpeg -f lavfi -i testsrc2=...`.
- Docker builds and the real deploy run from Windows.
- **Embedded UI**: `server/internal/webui` embeds `dist/`, which is only a `.gitkeep` in git. The Dockerfile and release workflow copy `web/dist` there before `go build`. `COUCHSIDE_WEB_DIR` overrides it with a folder on disk.
- **Website**: `site/` (static HTML, the logo's tokens from `docs/style.md`) is published to https://couchside.app by `.github/workflows/pages.yml`, which copies the icons in from `web/public`. The custom domain is set in the repo's Pages settings.
- **Releases**: push a `v*` tag. `.github/workflows/release.yml` builds zips (linux/darwin amd64 and arm64, windows amd64), the Windows installer, a multi-arch ghcr image, the Helm chart (pushed to `oci://ghcr.io/<owner>/charts/couchside` after the image), and a GitHub Release with `SHA256SUMS.txt`. CI also runs govulncheck, `npm audit --omit=dev --audit-level=high` and a chart lint/render job (with the guards that must fail); `docker.yml` reports Trivy findings without failing. A `pre-*` tag (`pre-0.17.0-1`) runs `prerelease.yml` instead: vet/test, the web build and the installer only, kept as workflow artifacts (no GitHub Release). Tag builds sign `couchside.exe` and the installer with Azure Artifact Signing (`windows-installer.yml`): the job runs in the `release` environment (admits `v*`/`pre-*` tags, and waits for the owner to approve each run), whose OIDC subject is a federated credential on the `RoboMouse-GitHub-Signing` app, which holds the Certificate Profile Signer role on `robododd-sign` (profile `robomouse-public`); without them a `pre-*` or manual build is unsigned with a warning and a `v*` build fails, so nothing unsigned is released. Both signatures are checked with `Get-AuthenticodeSignature`, and the signed `couchside.exe` (artifact `windows-exe`) replaces the cross-built one in the Windows zip before `SHA256SUMS.txt` is made. `ci.yml` runs vet, test and the web build on pushes and PRs; `docker.yml` builds the image (amd64, no push) when the Dockerfile changes. A release runs vet and test first (`verify`), and the container waits for the web build. Every action is pinned by commit SHA (version in a comment) and base images by digest; Dependabot updates both. CI and the release use `server/go.mod`'s Go and the Dockerfile's Node and run `go test -race`; `verify` also checks the notices file is current, and the tag must be on `main` with the chart's `version` and `appVersion` matching it, and `CHANGELOG.md` must have a `## <version>` section (breaking changes and upgrade notes first). Comskip is cloned by tag and checked against `COMSKIP_COMMIT`. Icons live in `web/public/icons/logo-<size>.png`, plus `favicon.ico`, `apple-touch-icon.png` and `site.webmanifest`. They're generated from `branding/logo-c-original.png` by `python3 branding/make-icons.py` (Pillow): the C is re-centred on its navy, rounded tiles for 64px and up (C at 72%), a bigger C for 16/32/48 and the .ico (86%), a full-square apple-touch-icon because iOS rounds it itself, and `icons/maskable-512.png` (full-bleed navy, the C at 60%, the manifest's maskable icon). `branding/make-transparent.py` cuts the C out onto transparency (`branding/logo-c-transparent.png`).
- **Windows installer** (`deploy/windows/couchside.iss`, Inno Setup 6, built by the reusable `windows-installer.yml` on a Windows runner): bundles jellyfin-ffmpeg (pinned version and SHA-256 in the workflow; chosen because upstream/Gyan 8.1+ builds need NVIDIA driver 610+ for NVENC), asks for the port (media is set up in the browser's first run), lists GPUs, writes `%ProgramData%\Couchside\couchside.env` (keeps other lines on upgrade), registers the `Couchside` service (`sc create … obj= "NT SERVICE\Couchside"`: its own virtual account, not Local System; `icacls` gives it Modify on `%ProgramData%\Couchside` and read on the program folder; an upgrade from Local System says on the finish page that share passwords need typing again, since DPAPI seals them per account; delayed-auto, restart on failure) and a program-based firewall rule. The binary runs as a service when the SCM starts it (`cmd/couchside/service_windows.go`): data defaults to `%ProgramData%\Couchside\data` and the log goes to `data\logs\couchside.log` (`logfile.go`, rolls at 10 MB). `config.Load` reads the settings file first (`internal/config/envfile.go`; `COUCHSIDE_CONFIG` overrides the path; real environment variables win) and finds `ffmpeg`/`ffprobe` beside the executable before the PATH. The icon is `deploy/windows/couchside.ico` (from `web/public/icons/logo-*.png`). To test-compile on Windows, install Inno Setup with `/PORTABLE=1` and run `ISCC /DAppVersion=… /DNumVersion=… /DStage=… /DOutputDir=… couchside.iss`. `ci.yml` runs vet, test and the web build on pushes and PRs; `docker.yml` builds the image (amd64, no push) when the Dockerfile changes. A release runs vet and test first (`verify`), and the container waits for the web build. Third-party actions are pinned by commit SHA (version in a comment) and base images by digest; Dependabot updates both. Comskip is cloned by tag and checked against `COMSKIP_COMMIT`. Icons live in `web/public/icons/logo-<size>.png`, plus `favicon.ico`, `apple-touch-icon.png` and `site.webmanifest`. They're generated from `branding/logo-c-original.png` by `python3 branding/make-icons.py` (Pillow): the C is re-centred on its navy, rounded tiles for 64px and up (C at 72%), a bigger C for 16/32/48 and the .ico (86%), a full-square apple-touch-icon because iOS rounds it itself, and `icons/maskable-512.png` (full-bleed navy, the C at 60%, the manifest's maskable icon). `branding/make-transparent.py` cuts the C out onto transparency (`branding/logo-c-transparent.png`).

## Architecture

- **One process, one pod.** The HTTP API and worker pool share a SQLite database in WAL mode. The Deployment uses `strategy: Recreate` because the DB sits on a ReadWriteOnce PVC. Don't scale replicas.
- **One at a time per key** (one fetch per remote image or person photo, one conversion per subtitle track): `internal/keylock`. Don't keep a `sync.Map` of mutexes and delete the entry on unlock; that lets two run together.
- **Backups** (`internal/backup`, `api/backup.go`, `cmd/couchside/restore.go`, web `components/settings/Backups.tsx`): a zip of a `VACUUM INTO` copy of the database plus `auth.key` and `server.id`, in `$DATA/backups`, daily (checked hourly by `Server.runBackups`; settings `backup.daily`, `backup.keep`, default 7) and on demand from Settings → System → Advanced (`/api/system/backups`, admin only). `db.Open` saves `couchside-upgrade-<time>.db` there before applying a migration to a database that already has data. `couchside restore <file>` puts one back with the server stopped.
- **Job queue** is the `jobs` table. A partial unique index dedupes active jobs, and `ClaimJob` runs `UPDATE ... RETURNING` in priority order: scan, match, artwork, still. The encode pool takes `optimize` and `commercials` (`encodeKinds` in `db/jobs.go`), commercials first. Kinds are defined in `internal/worker/worker.go`.
- **Scan flow:** walk, then `parse.Movie`/`parse.Episode`, then `probe.Probe`, then upsert. A newly created item enqueues `match`, which enqueues `artwork`. TV files enqueue `still`. After a completed scan, `catchUp` (`worker/catchup.go`) queues what existing files lack: stills, commercial detection for finished recordings, and preview thumbnails and intros where the library has them on, so files indexed before a feature existed (or was switched on) get it; a file whose job failed isn't queued again while that failure is in Activity. New per-file work belongs there too. Pruning uses `files.last_seen < scanStart` (`db.PruneLibrary`, which returns `Pruned`: a stale row with exactly one same-size twin of the same title and episode added by this scan is a rename, and `carryRenamed` moves its watch state, optimized copy, commercials, segments, chosen version, `added_at`, still and hand-pinned role to the new row first; `worker.TidyCache` then moves a renamed file's `cache/files/<id>` and deletes gone files' and items' cache folders, as library deletes do) and is skipped, failing the job, when any folder or file couldn't be read or when the walk found no videos in a library that has files (an unmounted share).
- **Parsing** (`internal/parse`) covers S01E02 with seasons up to 4 digits, 1x02, Plex-DVR date names (`Show - 2024-11-10 03 30 00 - Title.ts`), and bare E01 files. Date names become episode `YYMMDDHHMM` plus `episodes.air_date`. Unchanged files are re-parsed every scan (no probe), and re-indexed if the parse changed, so parser fixes reach existing libraries. A probe that times out (`probe.Timeout`, 60s) stores nothing and is retried next scan; `unreadable` files are probed again every scan. A completed scan re-queues `match` for the library's items still `pending` (their last match failed reaching the provider). Jobs still running at a restart after 3 attempts are failed, not re-queued; `ClaimJob` returns a nil job on any error. A job that fails for a passing reason (`worker.transient`: network, share I/O, timeouts, TMDB's 429; never a `usererr` or a refused key) is queued again with `not_before` (migration 0038), a minute after the first failure and doubling to an hour, until it has been tried 5 times (`maxRetries`).
- **Matching** never trusts a provider's fuzzy title lookup. `metadata.pickBest` scores candidates from exact lookup with and without year, plus search with and without year, on normalized title and year. Title variants ("3.10" to "3:10", " - " to ": ", "&" and "and") are tried when the result is missing or only partial. `imdb_pinned` marks "Fix match" choices, which automatic re-matches keep.
- **Seek-bar thumbnails** (`worker/trickplay.go`, `api/trickplay.go`, web `lib/trickplay.ts` and `SeekBar`'s `preview`): for libraries with `libraries.trickplay` on (Libraries → Edit), a `trickplay` job (encode pool, lowest priority) writes `$CACHE/files/<id>/trick/{0.jpg…, index.json, index.bif}`: ffmpeg writes one JPEG per 10s (`grabFrames`: keyframes only, in `yuvj420p` for the JPEG encoder; a file whose keyframes yield nothing (ffmpeg may well exit 0 with no output) is decoded in full, about 6 minutes for a two-hour 1080p remux on an N100; a run that stops part way (ffmpeg 8 can't re-set its filters for the malformed frames in a damaged broadcast stretch) resumes a slot later), and Go tiles them 10×10 per sheet (`writeSheets`), repeating the previous frame for empty slots; `index.json` records the file's size and mtime, and thumbnails of a changed file aren't served. `GET /api/files/{id}/trickplay` and `/trickplay/{name}`. The BIF is for the Roku.
- **Intro and credits** (`db/segments.go`, `api/segments.go`, `probe/chapters.go`, `internal/audiofp`, `worker/intros.go`; web `useIntroSkip`): `file_segments` holds one intro and one credits mark per file with a `source`: `chapters` (names like Intro / Opening / End Credits, read with `ffprobe -show_chapters` the first time `GET /api/files/{id}/segments` is asked, once per size+mtime), `detected` (an `intros` job per series, encode pool: `audiofp.Fingerprint` on 8 kHz mono PCM of each episode's first 10 minutes, `audiofp.Common` between neighbours in a season; `intro_checks` records files done; queued after scans for TV libraries with `libraries.intros`, or by `POST /api/items/{id}/intros`), or `manual` (admin `PUT`/`DELETE /api/files/{id}/segments/{kind}`). Manual is never replaced; chapters beat detected (`SetSegment`). The player shows Skip intro / Next episode pills; pref `intros` is button (default), auto or off.
- **Dynamic range** (migration 0036, `files.dynamic_range`/`dv_profile`, `probe.Info.DynamicRange`, `worker/dynamicrange.go`; web `components/RangeChip.tsx`, `lib/quality.ts` `rangeLabel`/`rangeShort`): `dv`, `hdr10`, `hlg` or `''` (SDR), written by the scan from ffprobe's colour transfer and Dolby Vision side data. NULL means not read yet: `catchUp` queues one `dynamicrange` job per library (ref: library id) for files indexed before it existed, which probes them (a file it can't read is recorded as SDR so the job doesn't return every scan). `ItemSummary.dynamicRange` is the best among a title's non-extra files (rank in `summaryCols`, named by `rangeScanner`). Shown as a chip on the title, episode and Files card, in version names, as a DV/HDR badge on posters, and as a chip on the Roku's Details. HDR10+ isn't told apart (its metadata is per frame).
- **Unplayable files** get `files.problem` (`unreadable` or `no-video`, usually DRM iTunes files). They get no stills, optimize or HLS, and the UI explains why.
- **Grouping key** is `(kind, parsed_title, parsed_year)` across libraries (migration 0031 merged items that were split by library), where `parsed_year` is 0 when unknown; `EnsureItem` looks across libraries first, under `ensureMu`. `media_items.library_id` is the title's home (where it was first seen; Manage view, re-match, `Item.libraryId`), while each file has its own `library_id`: per-profile library access, library counts, Manage rows and virtual-channel filters go by files, and `tidyItems` (after prunes, deletes and `DeleteLibrary`) drops items and episodes left without files and re-homes an item whose home library has none of its files. Metadata overwrites `title`, but grouping always uses the parsed fields.
- **File roles** (movies only; `files.role`, `part_no`, `extra_title`, `role_pinned`): `copy` (default; extra copies are duplicates), `part` (a movie split across files) or `extra` (bonus material). `parse.MovieRole` guesses from the path relative to the library root: an extras folder inside a movie folder (`Featurettes/`, `Trailers/`…; at the root it's just a folder of movies), a Plex suffix (`-trailer`), an extras word (`Behind the Scenes`), or a part marker (`Part 2`, `cd1`, `Disc Two`). Markers that are in the parsed title (`Deathly Hallows Part 2`, `The-Big-Short`) don't count. The scan uses `MovieIn`/`MovieRoleIn` with a folder lister (`videosIn`): an extras folder counts only under a folder named like a film with a year or holding a film file (`Pixar/Shorts` is a folder of films), and a part marker only when another file beside it has one. TV skips extras-named folders except directly under the root (a show called "Extras"); sample clips are `sample`, a `-sample`/`.sample` suffix, or anything in a `Sample` folder, under 300 MB. `refreshRole` applies the guess to unchanged files on every scan unless `role_pinned`. **Editions:** `parse.Edition` reads the cut from a `{edition-…}` tag or a word after the year (Extended, Director's Cut…) into `files.edition` (also refreshed there); copies with different editions are versions, not duplicates (`ManageRow.editions`), and a profile's choice of copy is `profile_versions` (`PUT /api/items/{id}/version`, `versionFileId` on the item detail). `PUT /api/files/{id}/role` pins a hand-picked role; marking part 2+ with no part 1 makes the item's single other copy part 1. Extras aren't counted in `fileCount`/`watchedCount`, "mark watched", backdrops or duplicate counts, get stills, and play as "Movie - Extra". `PlayInfo.parts` lists the parts (best copy of each); the player draws one timeline across them (`Timeline.parts` in `PlayerFrame`), seeks across parts by navigating with a module-level `partStart`, and always continues into the next part.
- **Settings sections** (`stores/router.ts` `SETTINGS_SECTIONS`, `components/settings/sections.ts`, `pages/SettingsPage.tsx`): `/settings` is every profile's own preferences and account; admins also get `/settings/{system,server,console,accounts,metadata,livetv}`, listed under Settings in the sidebar while a Settings page is open (`.subnav`) and as tabs on phones. Users who open another section see their own. Each section's cards are their own component in `components/settings/`. Rarely-needed cards go in the section's own collapsed **Advanced** area (`AdvancedArea.tsx`, `.advanced-toggle`): Accounts → single sign-on, System → backups, Live TV → recording padding and commercial-skip timing, Server → the `Editable` settings marked `Advanced`. There is no separate Advanced page; `/settings/advanced` lands on System.
- **Settings → Server** (`config/editable.go` `Editable`, `api/serversettings.go`, `components/settings/ServerSettings.tsx`): environment variables admins can set from the web. Saved values are `settings` rows `env.<VARIABLE>` (`db.EnvOverrides`); `config.LoadWith` reads them in place of the variables (only keys in `Editable`: never the port, data/cache/web folders, `COUCHSIDE_AUTH` or the programs the server runs (ffmpeg, ffprobe, comskip and its ini); `serve` deletes saved rows for keys no longer editable), and `Setting.Check` validates before anything is saved. They apply at start-up: `POST /api/server/restart` cancels `serve`'s context and `main.run` runs it again in process (sessions survive; playback stops). A start that fails with saved values (`errSavedSettings`) starts again without them and the page shows why (`startFailed`). Add a setting by appending to `Editable`; anything read at start-up from `cfg` picks it up. 
- **Media locations** (migration 0035 `media_locations`, `db/locations.go`, `api/locations.go`, `components/settings/MediaLocations.tsx`, in Settings → Server and the first run): where media can be. Libraries (`checkPath`), the DVR folder and virtual-channel filler must be inside one (`underRoot`/`within`; the DVR's own default folder is always allowed). `cfg.MediaRoots` come from `COUCHSIDE_MEDIA_ROOT` (PATH-separated list, containers) and show as fixed; the rest are saved. `PrepareLocations` runs in `serve` before anything reads media: once (`media.locations_init`) it imports a `COUCHSIDE_MEDIA_ROOT` that came from the settings file (`config.FromFile`; the old installer wrote it) and, when there are no locations at all, the outermost library folders, so upgrades refuse nothing; then it signs in to shares. **Network shares** (Windows only, `internal/netshare`): a location whose path is `\\server\share…` can carry a user name and a DPAPI-sealed password (for the service's account, so a copied database can't open it); `WNetAddConnection2` signs in to the share root (retrying after a disconnect on error 1219, a sign-in to that server with other credentials). Adding a location signs in and checks the folder opens first (`statWithin`, since an unreachable NAS can hang a stat); removing one refuses while a library would be left outside every location, and signs out of the share when no other location uses it. Elsewhere `netshare.Supported` is false and the share option is hidden: Docker, Helm and Linux mount shares themselves. **Folder browsing** (`GET /api/fs`, admin, `components/FolderPicker.tsx`) returns whole paths (`dirs: [{name, path}]`), starts from the locations and stays inside them; `all=1` (adding a location) goes anywhere, starting from the drives on Windows (plus shares in use) or `/`.
- **First run** (`api/firstrun.go`, `pages/WelcomePage.tsx`, `pages/FirstRunMediaPage.tsx`): `GET /api/auth` reports `firstRun` until the setting `setup.complete` is set (migration 0035 sets it on servers already in use). With passwordless sign-in, `POST /api/auth/welcome` names the oldest admin profile, optionally gives it a password, and signs the browser in (refused once that profile has a password or setup is done); with accounts the setup-code page names the admin instead. Until setup is done, `welcome` and `pick` from a public address (`localClient`: not loopback, private, link-local or CGNAT, after `realIP`) answer 403 `code: "private_only"`; `welcome` accepts them with the setup code (printed at start-up during the first run by `firstRunCode`, shared with `setupNeeded`, spent on use) and a password. `GET /api/auth` sets `remoteFirstRun` so the welcome page asks for both. Then admins see the media step until `POST /api/setup/complete`.
- **System → over time** (`GET /api/system/history?range=15m|1h|6h|24h`, `sysstat.History`, `components/settings/SystemHistory.tsx`, `components/LineChart.tsx`): a goroutine started by `Server.Run` reads its own `Sampler` every 5s (so `/api/system`'s averaging isn't disturbed) and keeps 5s points for an hour and 1-minute averages (peaks for counts) for 24h, in memory only. Points hold whole-scope, Couchside and ffmpeg/comskip CPU and memory, encoder processes, and streams (`streamCount`: HLS sessions plus live TV channels). Charts are plain SVG (no chart library), scaled to the data, broken at gaps.
- **Diagnostics** (`GET /api/system/diagnostics`, admin, `api/diagnostics.go`; web `components/settings/Diagnostics.tsx` under System → Advanced): a zip for bug reports, each part made on its own (a failure becomes `<name>.error.txt`): versions and features, `config.Config` with API keys masked, encoder detection, tool versions, counts and libraries, `db.MigrationReport`, `db.Health` (`quick_check`, size), free space (`internal/diskfree`) for data, cache, recordings and each library, the last 50 failed jobs, and the log buffer. Never auth.key, server.id, sessions or accounts.
- **System → Console** (`GET /api/system/logs?after=<seq>`, `internal/logbuf`, `components/settings/Console.tsx`): `main` wraps the stdout text handler with `logbuf.Buffer.Handler`, which keeps the last 2000 records (time, level, msg, attrs formatted like the text log) and passes everything on; `api.Server.UseLogs` hands it over. `gap` is set when lines after `after` were dropped or the server restarted. The page polls every 2s, filters by level and text, pauses, and follows the bottom until you scroll up.
- **Settings → right now** (`GET /api/system`, `api/system.go`, `web/src/components/settings/ServerNow.tsx`): CPU and memory come from `internal/sysstat` (cgroup v2 `cpu.stat`/`cpu.max`/`memory.current` minus `inactive_file` when `memory.current` exists, otherwise `/proc/stat` and `/proc/meminfo`; per-process CPU from `/proc/<pid>/stat` for Couchside and its `ffmpeg`/`comskip` children). CPU is averaged since the previous call, or over a 250ms pause when that was more than 10s ago. Windows (`sysstat/read_windows.go`) uses `GetSystemTimes`, `GlobalMemoryStatusEx` and a Toolhelp process snapshot (`GetProcessTimes`, `K32GetProcessMemoryInfo` working set); other platforms report `available: false`. Who's connected is in-memory (`api/presence.go`): a client is profile + IP + user agent, touched by every `/api` request (the status poll keeps it alive, 75s window). Playing state comes from progress reports, which now carry `state` (`playing`/`paused`/`stopped`) and `mode`; live TV and recordings are set by `tvWatch`/`dvrWatch` and kept alive by playlist polls.
- **Metadata providers** implement `metadata.Provider` and run in order through `metadata.Chain`: TMDB (`metadata/tmdb.go`) first, OMDb as a fallback. Responses are cached in `provider_cache` (TMDB TV for 3 days, the rest 30). Not-found answers are cached; bad-key, rate-limit and quota errors are not. When a provider errors and a later one answers, `Chain.Lookup` returns the answer with `skipped` set; `match` then keeps the item's credits and backdrop link and leaves it `pending` (`db.Metadata.Partial`), so a TMDB outage can't wipe them and the next scan matches again. The IMDb id stays the item's identity: TMDB fills `Details.ImdbID` from `external_ids`, resolves IMDb ids through `/find`, and uses `tmdb:movie:<n>` / `tmdb:tv:<n>` (`metadata.TMDBID`) for titles IMDb lacks; OMDb ignores those. TMDB backdrops land in `media_items.backdrop_url` and the artwork job downloads them, grabbing a video frame only when there's none. The TMDB key: `TMDB_API_KEY` (`off` disables), else `config.builtinTMDBKey`, stamped by `-ldflags -X` in release builds from the `TMDB_API_KEY` repo secret (a Docker build secret, never a build arg). `/api/status` reports `tmdbKey` (builtin/custom/""). A 401 is `metadata.ErrBadKey`: TMDB isn't asked again for 10 minutes, doubling to 6 hours, until it answers (`badKeyUntil`); `Chain.Degraded()` is `/api/status` `metadataDegraded` (and feature `metadataDegraded`), and match jobs and the Match picker answer `BadKeyMessage`. TMDB requires the attribution line and logo (`web/public/brand/tmdb.svg`) shown in Settings → Metadata and on the website.
- **Artwork** lives in `$CACHE/items/<id>/{poster,poster-thumb,backdrop}.webp` and `$CACHE/files/<id>/still.webp`. URLs carry `?v=updatedAt` for cache busting. `poster.src`/`backdrop.src` record the link each came from, so a re-match with the same link doesn't download again (uploads and frame grabs remove them).
- **Everything pulled from the internet is cached on the server**; clients never fetch from third parties. Provider responses are in `provider_cache`; artwork as above; cast photos in `$CACHE/people/<id>.webp`, fetched on first request (`worker.PersonPhoto`) and removed with the person when no title credits them any more (`db.PrunePeople`, daily); and any other remote image (channel logos, guide/recording/series art, the match picker's posters) goes through `GET /api/artwork/remote?u=` (`api/remote.go`), which fetches once into `$CACHE/remote/<sha256 of the canonical URL>`, only from allowlisted hosts (`remoteimg.Hosts`: https only, query dropped from the key except for SiliconDust hosts, redirects must stay on the list), keeps only bytes that sniff as JPEG/PNG/WebP/GIF, serves them with `nosniff`, remembers failed URLs for 10 minutes, and prunes images unused for 90 days and then least recently used past 2 GB (daily, and straight away when a fetch takes the cache past the cap: `Server.remoteSize`). The worker's artwork `download` uses the same allowlist and redirect rule. `db.ImageURL` fields marshal to those cache paths, so a new remote image field should use that type (or `db.CachedImage`). The Roku resolves them with `imageUrl()`.
- **Hand-set details** (`media_items.overrides`, migration 0033; `db.Overrides`, `details.go`): title, year, plot, genres and rated set by an admin (`PUT /api/items/{id}/details`; the title page's "⋯" → Edit details, and the Manage panel) are stored as JSON and laid over the provider's answer in `ApplyMetadata` and kept through `ClearMatch`, so no re-match undoes them. A field sent as null/omitted is cleared; when one was cleared on a matched title the API queues a match to bring the provider's value back. `Item.overrides` tells the form which fields are hand-set. Extras made by Merge are queued a `still` right away.

The web gets cookies: `couchside_access` (Lax, `/`), `couchside_refresh_<profile>` (Strict, `/api/auth`, one per signed-in profile so a browser can switch), and `couchside_profile` naming the active one; TV apps get JSON tokens and send Bearer. Client addresses and HTTPS come from `realIP` (`api/proxy.go`), which believes `X-Forwarded-For`/`X-Real-IP`/`X-Forwarded-Proto` only from peers in `COUCHSIDE_TRUSTED_PROXIES` (right-most untrusted hop); `GET /api/auth` sets `insecure` for plain HTTP from a public address and the sign-in page warns. A 500's text is shown only for `usererr` errors (`internal/usererr`, used for live TV and transcode messages written for users); anything else answers "internal error" and goes to the log, so return `usererr.New` for a message the UI should show. Handlers that answer a service error as a 400 use `userFault(err)`, which does that only for `usererr` messages; never put `err.Error()` of anything else in a response (paths, SQL, ffmpeg output). Codes live in memory for 10 minutes. Frontend: `api()` refreshes once on a 401 and retries; `stores/auth.ts` renews 2 minutes before expiry, counted from `expiresIn` (seconds left, sent with every sign-in, refresh and `GET /api/auth`) so the browser's clock doesn't matter (cookies also feed `<video>`, `<img>` and hls.js); `App` shows Setup, SignIn (the profile picker; a locked profile asks for its password) or ChangePassword pages before loading the profile and starting the status poll; `useIsAdmin`, `useCanRecord` and `useOwnerCheck` hide controls the server would refuse.

## Encoding (internal/transcode, worker/optimize.go, web PlayerPage)

- **Decision** happens client-side in `web/src/lib/playback.ts`. It uses canPlayType for direct play, then the optimized copy, then HLS. The server then decides copy vs encode per stream in `transcode.Manager.Create`. Video is copied for 8-bit H.264 that isn't HDR, or for any codec in the request's `videoCodecs` (ffprobe names; the Roku sends the file's codec when it decodes it, so a 4K HEVC film with TrueHD only has its audio converted), and only when it doesn't need downscaling. Audio: AAC/MP3 is copied when the client allows; with the request's `audioCodecs` (`ac3`, `eac3`; a TV with a receiver) such a track is copied too and other multichannel audio becomes 5.1 E-AC-3 (or AC-3) rather than stereo AAC (`Session.AudioOut`).
- **HLS sessions**: the playlist is synthesized up front, with `SegDur` = 4s and every segment listed. Segments are generated on request. A request outside the current ffmpeg run restarts ffmpeg with `-ss N*4 -copyts -start_at_zero` and `-force_key_frames expr:gte(t,n_forced*4)`. When both streams are encoded, it seeks 10s early (`seekPreroll`) and trims back with `trim`/`atrim=start=N*4` (metadata-only, so VAAPI frames are fine): seeking in MPEG-TS starts video at the next keyframe, seconds late, and on VAAPI MPEG-2 the first segment came out audio-only, which stalls hls.js. `t` is relative to the run's first frame, so don't add the start offset. Remuxed segments follow source keyframes, which hls.js tolerates.
- ffmpeg is SIGSTOPped when more than 30 segments ahead (10 for a remux, whose segments follow the source's keyframes and run long) and killed after 90s idle. Segments more than 15 behind the player are deleted every 2s (`trimBehind`), so a long session doesn't fill the cache; one asked for again is made again (`ensureRun` restarts ffmpeg at a missing segment at or below `hi`). Sessions expire after 3h and are wiped on start. At the limit, a session idle 20s or more is evicted. The limit counts sessions with a running ffmpeg or a request in the last 90s; it's checked and the slot taken under one hold of `Manager.mu` (probing happens before), and again when `Segment` has to start ffmpeg for a session that has none. `Session.restartMu` (taken before `mu`) serialises stop/start, and a closed session never starts again.
- **Optimize** jobs (`kind=optimize`) run in their own worker pool (`ClaimJob(ctx, encode=true)`), so scans are never blocked. Progress comes from `ffmpeg -progress pipe:1`. Cancel deletes the job row. Output goes to `$CACHE/optimized/<fileId>.mp4`, recorded relative to the cache (`OptimizedRel`, forward slashes; read through `ResolveCache`) so a moved cache keeps its copies; `cleanupOptimized` rewrites older absolute rows at start-up. A changed file drops its optimized copy, and orphans are cleaned at startup.
- **Threads**: every ffmpeg that converts video gets `-threads` (`transcode.ThreadArgs`): `Encoder.Threads` = `cfg.LiveThreads()` (cores ÷ `MaxTranscodes`) for playback and live TV, `cfg.JobThreads()` (2) for optimize and preview thumbnails; `COUCHSIDE_FFMPEG_THREADS` overrides both. Remuxes and passthrough get none. The image and chart set `GOMEMLIMIT=1GiB` (Helm `goMemLimit`).
- **Hardware**: `transcode.Detect` runs a one-frame test encode and falls back to software. `COUCHSIDE_HWACCEL` defaults to `auto` (`autoCandidates`: Windows nvenc, qsv; Linux vaapi when the render node exists, nvenc, qsv), but the Dockerfile, compose file and Helm chart set `none`. `Encoder.Note` keeps ffmpeg's reason for each encoder that failed (`ffmpegReason`), shown in Settings → System. For VAAPI it also tests the full GPU pipeline (`testHWDecode`: encode a clip on the GPU, then decode + `scale_vaapi` + encode it), setting `Encoder.HWDecode`, and `HWTonemap` when ffmpeg has `tonemap_vaapi`. With `HWDecode`, sessions use `vaapiFull` (`-hwaccel vaapi -hwaccel_output_format vaapi`, `scale_vaapi`, `tonemap_vaapi`, `h264_vaapi`), so 4K HEVC HDR never touches the CPU; without GPU tone mapping only the scaled frames are downloaded for zscale. A session whose GPU run fails falls back to CPU decode for good (`Session.gpuFallback`); burned-in subtitles always use the CPU path. Live TV uses the same GPU pipeline (`deinterlace_vaapi=auto=1`, `-bf 0`), retuning with CPU decoding if the GPU run fails before the first playlist; optimize still decodes on the CPU. NVENC has the same shape (`nvencFull`, also verified by `testHWDecode`): `-hwaccel cuda -hwaccel_output_format cuda`, `yadif_cuda`, `scale_cuda` (its `format` option needs ffmpeg 7+), `h264_nvenc`. HDR uses `tonemap_cuda` (jellyfin-ffmpeg) or `tonemap_opencl` (NVIDIA's OpenCL, via `hwdownload`/`hwupload`, since OpenCL can't map CUDA frames), whichever passes `testCUDATonemap` on a synthetic PQ clip (`Encoder.TonemapFilter`), else zscale on the scaled-down frames. Quality presets (`lib/playback.ts` `PRESETS`, Plex's ladder: 1080p 20/12/10/8, 720p 4/3/2, 480p 1.5, 360p 0.7 Mbps) send `bitrateK` with the height to `POST /api/files/{id}/hls`. On Intel iGPUs use VAAPI (the iHD driver is in the image) through a GPU device plugin (Helm `hwaccel.dri.resource`, e.g. `gpu.intel.com/i915`; the default path) or `/dev/dri` mounted into a privileged container (`hwaccel.dri.enabled` + `privileged`, which the chart refuses without `privileged`; non-root and drop ALL stay either way), and `supplementalGroups` set to the host gids of `/dev/dri/renderD128` and `card*`.
- **Play queue** (`stores/queue.ts`, `PlayerFrame.queue`, `components/player/QueueMenu.tsx`): entries are `{fileId, title, subtitle}`, explicit from Play all or implicit (built by `PlayerPage` when the file isn't in the queue: the season of the episode playing, or a movie's extras when one of them is playing; a film on its own clears it). The frame shows Previous (P: start over after 5s, else the entry before; disabled at the first entry's start), Next (N) and, with two or more entries, a Queue button (Q) whose overlay pauses the video, lists the entries with the current one marked, jumps on click, removes with ×, and resumes on close. `onEnded` follows the queue before next-episode autoplay.
- **Player UI** is `web/src/components/player`. `PlayerFrame` owns the `<video>`, controls, keyboard, auto-hide and full screen (on its root, which is `data-theme="dark"`). `SettingsMenu` takes `SettingSection[]`, and `useMediaState` snapshots the video. Pages (`PlayerPage`, `LivePlayerPage`, `RecordingPlayerPage`) only own sources and settings. Timelines are `vod`, `live` (seekable range, GO LIVE via `hls.liveSyncPosition`; the bar spans the guide program the playhead is in (or its half-hour slot when the guide has none), in clock time where the live edge is now, with the time before tune-in hatched and unseekable via SeekBar `availableStart`), or `recording` (wall-clock start/end, with a hatched unrecorded part).
- **Tracks**: `GET /api/files/{id}/streams` lists audio and subtitles, including sidecars (`x<N>` keys). `GET /api/files/{id}/subtitles/{s|x}<N>.vtt` converts to WebVTT, cached as `$CACHE/subs/<file>-<key>-<mtime>.vtt`. Embedded tracks are fetched by the player in 90s chunks (`s<N>.c<K>.vtt`), because a whole track means reading the entire file: 7 minutes for a 30 GB remux over SMB, versus about 7s per chunk. Chunks use `-ss from -copyts -start_at_zero … -to <absolute end>`, since an input `-t` is ignored with copyts. The player dedupes cues across chunk overlaps. A TV app, whose player fetches a whole track by URL, asks for `s<N>.vtt?async=1` first: 202 (`Retry-After`) while `convertInBackground` runs (30 min limit, one per track), then 200; a failure is remembered for 10 minutes (422). `?prepare=1` starts the same conversion but only answers `{"ready": bool}`; the Roku polls it, then gives its player the plain URL. Conversions run at most 3 at once (`subSlots`; others wait while their request lasts), chunks past the file's duration are 404, sidecar caches are keyed by the sidecar's own name, size and mtime, `$CACHE/subs` files unused for 30 days are pruned daily, and ffmpeg's stderr goes to the log, not the client. HLS sessions take `audioIndex` (`-map 0:a:N`) and `burnSubtitle`. Burn-in uses `-filter_complex [1:s:N][0:v:0]scale2ref=w=main_w:h=main_h…overlay` with a **second input seeked 10s earlier**, because PGS captions need earlier data. ffmpeg 6.1's scale2ref uses `main_w`/`main_h`, not `rw`. `Encoder.VideoParts` returns the bare filter chain for this.
- Test media for the tricky paths: HEVC 10-bit + AC3 in MKV (transcode), H.264 in MKV (remux), and HEVC tagged smpte2084 (tone map). Generate them with ffmpeg lavfi.

## Live TV & DVR (internal/livetv, web components/livetv, LivePlayerPage)

- It's off unless `COUCHSIDE_HDHOMERUN` is set. The HDHomeRun HTTP API supplies `discover.json`, `lineup.json` and `status.json`. Stream URLs come from the lineup (`:5004/auto/v<ch>`), and HTTP 503 means every tuner is busy.
- **Guide**: `api.hdhomerun.com/api/guide.php?DeviceAuth=...&Start=<unix>`, about 4h per page, paged to about 26h. It **rejects Go's default User-Agent with 403**, so keep the explicit UA. DeviceAuth rotates, so re-read `discover.json` before each fetch and never expose it.
- **Channel prefs**: `channels.pinned` (via `PUT /api/livetv/channels/{n}/pin`) sorts first in `Channels()`. `signal_strength`/`signal_quality` come from the lineup's scan readings on each refresh. `ReplaceChannels` upserts, so pins survive lineup refreshes. Filtering is client-side, in `components/livetv/filters.ts` and `FilterBar.tsx`, with state shared by the Guide and Channels tabs and kept in localStorage.
- **Live passthrough**: `POST /api/livetv/watch` (and recording watch) take `videoCodecs`/`audioCodecs`, the codecs the client decodes (`livetv.NormalizeCodec` names: mpeg2, h264, hevc, ac3, eac3, aac). When the channel's lineup codecs are in them, `Spec.CopyVideo`/`CopyAudio` repackage the broadcast into HLS with `-c copy` (segments cut at its own keyframes; the client deinterlaces). The Roku sends what `roDeviceInfo.CanDecodeVideo/Audio` allow unless the profile pref `livePassthrough` is false; browsers never do. Sessions are shared per channel + height + copy flags.
- **Live**: one ffmpeg per channel and height, shared by viewers; concurrent tunes of the same stream wait for one start (`liveManager.starting`). Heights snap to the presets (`snapHeight`: 360/480/720/1080; 0 is "Auto", the broadcast's own size, from `WatchOpts.Source` / the request's `source: true`; library channels still use 720 then). A height is a cap: with the source size unknown the scale is `min(ih,H)` (`transcode.VideoOpts` with `SrcHeight` 0), so nothing is scaled up, and the bitrate comes from the smaller of the cap and `Spec.SrcHeight` (probed for stream channels, guessed from the lineup's HD flag otherwise: `guessHeight`). and streams that convert video are capped at `COUCHSIDE_MAX_TRANSCODES` (`ErrBusyEncoding`, 429); passthrough isn't counted. Tuner streams keep a 3-hour sliding window of 2s segments (`liveWindow`, `delete_segments`); recordings watched from the start keep an EVENT playlist. It deinterlaces with yadif (interlaced frames only), and waits for the first playlist before returning. It's reaped 20s after the last request. libx264 runs with `-tune zerolatency` (`VideoOpts.Live`) so segments arrive evenly. The player sits 8s behind the edge (`liveSyncDuration`, no playback-rate catch-up) and `useLiveCushion` holds playback until 6s are buffered, at the start and after any stall, instead of stuttering at the edge. It measures encoder speed from playlist growth (LEVEL_UPDATED `totalduration` over wall time) and warns below 0.95×.
- **Recordings folder**: the `settings` table key `dvr.recordings_dir` overrides `COUCHSIDE_RECORDINGS_DIR`; always call `Service.RecordingsDir(ctx)`, never `cfg.RecordingsDir`. `pathInDir` reuses a matching show folder (by `parse.Name` plus `Normalize`) and season folder. `ensureLibrary` uses the library that *contains* the folder, and only creates "DVR Recordings" when none does. Delete only removes the row's own `.ts` file, because the folder may be a shared TV library. The media mount is read-write for this; nothing else writes there.
- **Shutdown during a recording** leaves the `.partN.ts` files and the `recording` status alone. `recoverInterrupted` resumes into the same path, via `existingParts`, which also picks up a finished file from older builds, and joins everything at the end. Never finalize on `parent.Err()`, or the file splits in two.
- **Watch from start**: `POST /api/dvr/recordings/{id}/watch` runs a live-style HLS session whose input is the growing part file (`-follow 1`). The player uses `startPosition: 0`. Its ffmpeg ends about 30s after the recording does; the reaper (`liveManager.reap`) keeps such a `rec:` session, with its finished playlist, until the viewer stops asking, where a tuner stream whose ffmpeg has gone is removed at once.
- **Padding**: `Service.Padding(ctx)` reads `dvr.pad_before`/`dvr.pad_after` (seconds, set in Settings via `PUT /api/settings/timing`), falling back to `COUCHSIDE_DVR_PAD_BEFORE/AFTER` (default 10s). Each recording row stores its own pads; saving new padding also updates rows still `scheduled`.
- **Recording**: the scheduler ticks every 5s. It runs `ffmpeg -c copy -t <remaining>` into `.partN.ts`, retries on drops, and joins parts with `concat:`. Plex-style names are built in `recordingName`; the file is picked in `startRecording` under `pathMu`, after the series lookup. Due recordings start on their own goroutines (`starting`), and `MarkRecording` only moves a row that is still `scheduled`. Restart recovery lives in `recoverInterrupted`. When the parts can't be joined (a full disk), the row goes to `failed` but keeps the final path: the scan skips `.partN.ts` files any recording row owns (`RecordingOwnsPath`), Recordings shows Recover (`POST /api/dvr/recordings/{id}/recover`, `Service.Recover`) while parts are on disk, and Dismiss removes them. Each finished recording enqueues a scan of the auto-created "DVR Recordings" library, and `underRoot` allows the recordings dir outside `MEDIA_ROOT`.
- **Series rules** (`livetv/rules.go`, table `series_rules`) are keyed by the guide's SeriesID. `evaluateRule` walks upcoming airings and handles the cases in this order:
  - DRM and channel filter.
  - An existing recording at that airing: cancelled ones are never revived, and failed ones can be retried.
  - The mode.
  - The library check (`LibraryEpisodeKeys`) and the recorded check (`RecordedEpisodes`).
  - Same-episode repeats.
  - Tuner conflicts: skip this airing, and a later one can take the episode.

  Episode keys are `S11E4` (unpadded), or `t:<normalized show>|<normalized episode title>`. Rule-owned scheduled rows the rule no longer wants are deleted (`UnscheduleStale`), except anything starting within 30s. `LibraryMatchesFor` ranks same-titled shows by matching upcoming episode titles. Keep-last-N runs in `afterRecording`. Tests in `livetv/rules_test.go` run on a temp SQLite DB.
- **Same-titled series** (`livetv/identify.go`, `metadata/identify.go`, table `series_matches`): `showYear` identifies a recording's series with `metadata.IdentifySeries`. A single exact-title OMDb series wins; otherwise the program's `original_airdate` must fall in a series' run (±1 year); otherwise the season's episodes decide (title, or release within 2 days). The year is used only when `Shared` (another series has the title), so it goes into the show folder (`MacGyver (2016)`), which the parser and matcher already read. Results are stored per guide SeriesID: unknown ones are rechecked after 7 days, known ones after 30. A stored match that's due a recheck is still used when the recheck fails. Lookups are prefetched when a recording is scheduled (`prefetchShow`, from `Record` and rules) and done at start with an 8s timeout; a failure records under the plain name. `pathInDir` won't reuse a same-titled folder with another year, or a plain folder whose matched item (`FolderSeriesYear`) has another year.
- **Admin menus on the title page** (`components/item/AdminMenus.tsx`, `MenuButton` from `components/ui.tsx`): `TitleActions` (the "⋯" beside Mark watched: scan the library, optimize, find commercials or check again, Manage in library, delete from disk) and `EpisodeActions` (a "⋯" on each episode row, outside its play link: mark watched, re-scan, optimize, find commercials, delete). Re-scan is `POST /api/files/{id}/rescan` (`worker.RescanFile`: `indexFile` on the unchanged file, so probe, name, role and still are redone); `indexFile` only drops an optimized copy when size or mtime changed. `POST /api/files/{id}/optimize` queues one file even if it plays directly. Confirmations are `notify(text, "info")` (`.notice-info`).
- **Selecting titles** (`pages/LibraryPage.tsx`, `PosterGrid`'s `selection`, `components/manage/DeleteSelected.tsx`): on the Movies and TV grids an admin picks titles with Ctrl/Cmd-click (Shift-click for a range; while any are picked a plain click picks too, Escape clears). The header then shows the count and an Actions menu: Play all (a session play queue, `stores/queue.ts`: the movies' chosen copy or parts and the shows' episodes in grid order; `PlayerPage.onEnded` plays the next queued file before falling back to next-episode autoplay, and a poster click clears the queue), add to/remove from My list, mark watched/unwatched, Refresh metadata (`POST /api/items/{id}/match {refresh: true}`: re-matches without clearing a pinned IMDb id), Find commercials (when `status.comskip`), Merge (two or more: `components/manage/MergeTitles.tsx` → `POST /api/items/merge {into, from, as}`, `db.MergeItems`: movies' files become `copy` or `extra` of the kept film (extras named after the film they were), shows' episodes move by number; profile lists carry over; the other items are deleted), Manage (one title: `/libraries/{id}?item=<id>` opens its panel) and Delete, which confirms and calls `DELETE /api/items/{id}` per title, stopping at the first failure. Only picked titles in view count. Merged files get `files.item_pinned` (migration 0032): `FileStamp.ItemPinned` makes the scan skip `parseChanged` and role detection, `UpsertFile` keeps a pinned row's item and episode, and `indexFile` keeps `prev.MediaItemID` for them.
- **Library settings and the Edit panel** (`/libraries/{id}`, `pages/LibraryManagePage.tsx`, `components/manage/`, `api/manage.go`, `db/manage.go`): the library's name, folder and options (`components/LibraryForm.tsx`), Scan, Re-match, Optimize all and Remove, then every title as a table. `ManageRows` gives max/min file height, codec, size, distinct episodes and `sameImdb`; duplicates are extra files per movie or episode, or items sharing an IMDb id. A title's row links to `/item/{id}?edit=1`, which opens `ItemPanel` on the title page: Details by hand (`components/item/DetailsEditor.tsx`, `PUT /api/items/{id}/details`), Match (`GET /api/items/{id}/lookup` via `Chain.SearchTitles`; an IMDb id or URL looks up directly; picking a result reuses `POST /api/items/{id}/match`), Artwork (`PUT /api/items/{id}/artwork/{poster|backdrop}`, raw body, sets `media_items.custom_poster`/`custom_backdrop`, which the artwork job and `ClearMatch` respect) and Files (roles, extra copies, delete). The panel loads `GET /api/items/{id}/manage` (one `ManageRow` plus its library); the episode page opens it scoped to that episode's copies. Jobs and deleting the whole title are in the page's "⋯" (`components/item/AdminMenus.tsx`). Deletes remove files **on disk**: `deleteFiles` refuses paths outside the library folder (`insideDir`), removes subtitle sidecars, cache (optimized, still, item art) and DVR recording rows, then `DeleteFileRows` drops orphan items and episodes. `removeEmptyDirs` stops at the library root and reports folders that still hold non-video files.
- **Commercials** (`worker/commercials.go`, table `commercials`): `indexFile` queues a `commercials` job for a file whose path is a completed recording (`IsRecording`) and has no current result. The job runs `comskip --ini --output=<tmp> --output-filename=couchside` and parses the `.edl`. comskip may exit 1 on success or on error, so a missing `.edl` tells them apart. Results store the file's size and mtime and are ignored once the file changes. The default ini is written to `$CACHE/comskip/comskip.ini`. It's off when `COUCHSIDE_COMSKIP` isn't on PATH. The Dockerfile builds comskip V0.83 from source with a static argtable2, because Alpine has neither. `POST /api/items/{id}/commercials` (`{"redo"}`, admin) queues a whole series or movie via `db.CommercialCandidates` (playable, non-extra files without a current result, or all with redo); the title page's "⋯" calls it when `status.comskip` is true. In the player, `useBreakSkip` auto-skips, except for breaks the viewer seeked into (`allow`). The mode is the profile pref `commercials`. `GET /api/files/{id}/commercials` returns breaks already trimmed by the shared settings `commercials.skip_after_start` / `skip_before_end` (default 1s each, `api/timing.go`), so skips never cut into the show; breaks left under 1s are dropped. Before trimming, breaks less than `commercials.merge_gap` apart (default 60s) are joined, since comskip often splits a break around a promo it took for show; this applies at read time, so existing results benefit. A break starting in the first 5s (`leadInBreak`: the recording's lead-in from padding) is never joined to the next, because what follows it is the cold open, which can be under a minute. The default ini (`defaultComskipINI`) has detection settings similar to Plex's: `detect_method=43` (no silence cut points, which split sitcoms at every scene change), `min_show_segment_length=250`, `disable_heuristics=4`, and tuned brightness and logo thresholds. It finds the same breaks as Plex does on the same recordings; comskip's defaults flagged scenes as ads. `comskipINI` rewrites the cached file whenever the default changes. Ini changes only reach a file when it's checked again. Admins can right-click a break on the seek bar (`onBreakMenu` in `SeekBar`, `BreakMenu` in `PlayerFrame`) for "Not a commercial": `POST /api/files/{id}/commercials/dismissed` (`{start, end, restore}`) stores it in `commercial_dismissals` (migration 0020), apart from the detection result, and the GET hides any break (after merging and trimming) that a dismissal covers for half its length or more, so it stays hidden when detection runs again.
- Tuners can be shared with other DVRs (e.g. Plex). ATSC 3.0 channels with DRM (HEVC/AC-4) are listed but shown locked.
- **Virtual channels** (`livetv/virtual.go`, `virtual_stream.go`, `db/virtual.go`, `api/virtual.go`, migration 0017; web `components/settings/VirtualChannels.tsx` and `ChannelEditor.tsx`): Couchside's own channels from the library. Each has a `channels` row with `virtual_id` set (`Channel.Virtual`), so guide, lineup, favourites, search and both players treat it like a tuner channel; `ReplaceChannels` never touches those rows. `VirtualConfig` (JSON in `virtual_channels.config`) holds the filters, order (shuffle deck or sequential round-robin per show, kept in `state`) and `Filler` (a folder of clips, lengths cached in `filler_clips`; align to 15/30/60 min, padding at most 10 min; mid-program breaks). `extendVirtual` (serialized by `virtualMu`) appends `virtual_playout` pieces (ms, path, in-point, filler flag) and their guide `programs` 36h ahead, every 10 min; a program covers its own commercials. Streaming (`startVirtual`) is on demand: one ffmpeg per piece (`-ss in -t dur`, `-re` except a fast first run that gives the player 8s of buffer, `-output_ts_offset` so timestamps continue, `anullsrc` for files without audio; each file is probed once per session (`liveManager.pieceInfo`) so HDR is tone mapped and the GPU decodes when it can; every piece is scaled to the session height so the picture size doesn't change at the joins), merged by `mergedPlaylist` into a sliding 30-min `index.m3u8` with discontinuities. `virtualLoop` never runs ahead of the clock: a piece that won't play (file moved, share gone) or a file shorter than scheduled leaves the stream paused for the rest of its slot, retried every 30s, and the next program starts when the guide says; tuning in during such a slot waits for the next piece when it's under 12s away, otherwise answers when the channel carries on. `SaveVirtual`/`DeleteVirtual` change the channel under `virtualMu`, so a running extension can't put the old schedule back. The Live TV service now always exists: `HasTuner()` gates tuner-only features (refresh, DVR folder, rules, padding); `configured` is tuner or any virtual channel. Virtual channels can't be recorded. **Stream channels**: a virtual channel whose config has `stream: {url}` (`livetv.StreamSource`; http/https only, since ffmpeg would open a `file:` address) shows a live stream from elsewhere instead of the library. It has no playout: `extendVirtualLocked` only writes hourly guide entries with the channel's name (`streamGuide`), and `watchVirtual` calls `liveManager.startStream`, the tuner path (`startInput`, key `vc:<number>`, sliding window, always converted, counted against `COUCHSIDE_MAX_TRANSCODES`) with `-protocol_whitelist http,https,tcp,tls,crypto`, reconnects and an optional audio map (`Spec.stream`). The source is probed first (`streamInfo`, cached 10 min per URL; `streamSpec`): 8-bit H.264 is copied and AAC/MP3 stereo is copied, so an already-H.264 source (couchside-capture) isn't decoded or re-encoded and doesn't count as a transcode; anything else is converted. A source that fails answers "couldn't open channel N's stream: <reason>" without the address, which is logged. The editor's "Plays: Your library / A stream address" picks the kind. **Export and import** (`api/virtual_port.go`; the buttons in Your channels): `GET /api/livetv/virtual/export` downloads `{kind: "couchside-channels", version, channels}` with libraries by name and picked titles by title, year and kind (ids mean nothing on another server); `POST /api/livetv/virtual/import` resolves them (`channelNames.resolve`), replaces your channel with the same number, and answers `{created, updated, skipped, warnings}`. A channel none of whose libraries or titles are here is skipped, not imported unrestricted.

## Styling

- Colours: `docs/style.md` (tokens, contrast, rules). One dark theme, "seafoam as the primary": neutral dark grey surfaces, bright seafoam `--accent` as the only interactive colour, the logo's blue (`--good`) and sky (`--info`) for state, red (`--critical`) for recording, errors and favourites, amber warnings. There is no light theme (no theme store or toggle). Bright fills take `text-on-accent` (deep green), never `text-white`. Violet (`--secondary`), `--brand-pink` and `--brand-cyan` are avatar colours only.
- `web/src/index.css` starts from Portside Lite's component classes (`.card`, `.btn-*`, `.field`, `.navtab`, `.table`, `.tint-*`). Media additions follow the same naming: `.poster`, `.still`, `.row-title`, `.art-badge`, `.chip`, `.hero-fade`, `.poster-placeholder`.
- Put new reusable styles in `index.css` under `@layer components`. Don't hard-code colours; use the tokens.
- **Actions that can fail** go through `attempt("Couldn't …", fn)` (`lib/notices.ts`), which shows the server's message in a `.notice` (rendered by `components/Notices.tsx`, over everything). Modal dialogs use `useDialog(ref, onClose)` (`lib/dialog.ts`: focus in, Tab trapped, Escape, focus back) with `role="dialog" aria-modal="true"`.
- **Phones** (below `md`, `usePhone()` in `lib/media.ts`): `Sidebar` and `StatusBar` hide, and `MobileNav` shows a top bar (logo, search, profile) and bottom tabs (Home, Movies, TV, Live TV, More); the More sheet holds Activity, Libraries, Settings, profile and sign-out. Page side margins use `.gutter` (16px, 24px from md); `PosterGrid` fits three across. List pages put search first, with the rest in `FilterMenu` (a bottom sheet on phones, a dropdown on desktop) and active filters as removable `.choice` chips.
